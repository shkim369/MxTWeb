# MxTWeb 성능 개선 보고서

> Blazor Server 기반 사내 재고·실험 관리 시스템의 동시 접속 성능을 측정하고 개선한 기록입니다.
> 모든 수치는 개선 전/후 동일 조건에서 직접 측정한 값입니다.

## 요약

동시 접속 20명 기준:

| 지표 | 개선 전 | 개선 후 | 개선 |
|---|---|---|---|
| 칩 사용 대장 로딩 (p50) | 9.6초 | **1.6초** | **6.2배** |
| 칩 사용 대장 로딩 (p95) | 12.8초 | **1.9초** | **6.6배** |
| 서버 Live 메모리 | 3,744 MB | **289 MB** | **13배** |
| 사용자 1명당 서버 메모리 | 178 MB | **12 MB** | **14배** |
| 서버 CPU 사용 시간 | 127초 | **6.2초** | **20배** |
| DB에서 읽은 행 수 | 8,200,181행 | **2,540행** | **3,200배** |

그리고 데이터가 많을 때 **아예 열리지 않던 압력 테스트 탭**(120초 초과)이 **0.48초**에 열리도록 고쳤습니다.

## 1. 배경

MxTWeb은 Blazor Server로 만든 사내 웹 앱입니다. Blazor Server는 일반적인 웹 앱과 달리 **사용자마다 서버에 회로(circuit)가 하나씩 생기고, 컴포넌트 상태가 서버 메모리에 계속 남아 있는 stateful 구조**입니다.

그래서 동시 접속자가 늘면 다음 공식대로 서버 자원이 소모됩니다.

```
서버 메모리 ≈ 사용자 1명이 붙잡고 있는 상태 × 동시 접속자 수
```

데이터가 적을 때는 문제가 드러나지 않습니다. 하지만 몇 년치 데이터가 쌓이고 여러 명이 동시에 쓰면 어떻게 될지 확인이 필요했고, 감으로 고치기보다 **먼저 측정하고, 병목을 찾고, 고친 뒤 다시 측정**하는 순서로 진행했습니다.

### 테스트 데이터

운영 3년치를 가정한 별도 벤치마크 DB를 만들었습니다.

| 테이블 | 행 수 |
|---|---|
| ChipUsage (칩 사용 대장) | 20,116 |
| ChipPressure (압력 테스트) | 200,466 |
| CompHistory (부품 입출고 이력) | 100,100 |

### 측정 방법

- **실제 브라우저로 부하 생성**: Blazor Server는 WebSocket 위에서 동작하기 때문에, 일반 HTTP 부하 도구로는 실제 회로가 만들어지지 않습니다. 그래서 Headless Chromium으로 사용자마다 진짜 회로를 열었습니다.
- **시나리오**: 로그인 → 대시보드 → 칩 사용 대장 → (선택) 압력 테스트 탭. 각 사용자는 마지막 페이지를 연 채로 회로를 유지합니다.
- **공정성**: 매 측정마다 서버를 새로 띄우고, 예열(JIT, 커넥션 풀)을 위해 1명을 먼저 돌린 뒤 측정에서 제외했습니다.
- **측정 지표**

| 지표 | 측정 방법 |
|---|---|
| 페이지 로딩 시간 | 이동 시작부터 데이터 행이 화면에 표시될 때까지 (p50 / p95) |
| 서버 Live 메모리 | `dotnet-gcdump`로 Full GC를 강제한 직후 `dotnet-counters`로 GC 힙 크기 측정. 쓰레기를 제외하고 **실제로 붙잡고 있는 메모리**만 측정 |
| 서버 CPU 시간 | 측정 구간 동안 서버 프로세스의 CPU 사용 시간 |
| DB 부하 | SQL Server DMV(`sys.dm_exec_query_stats`)로 실행 횟수, 논리 읽기, 반환 행 수, 처리 시간 집계 |

## 3. 문제 진단

### 3-1. 페이지에 들어올 때마다 테이블 전체를 메모리에 올림

```csharp
// 개선 전: ChipUsagePages/Index.razor
protected override void OnInitialized()
{
    context = DbFactory.CreateDbContext();
    _filteredResults = context.ChipUsage.ToList();     // 2만 행 전체
    FilteredPresData = context.ChipPressure.ToList();  // 20만 행 전체 (첫 탭에서는 쓰지도 않음)
```

- 사용자 1명이 페이지에 한 번 들어오면 **DB에서 45만 행**을 읽었습니다.
- 이 데이터가 회로가 살아 있는 동안 서버 메모리에 남아서, **사용자 1명당 약 160~180MB**를 차지했습니다.
- `ToList()`가 동기 호출이라 DB 응답을 기다리는 동안 스레드가 묶여 있었습니다.

### 3-2. 압력 테스트 탭에 페이저가 없음

압력 테스트 그리드는 `Items`에 전체 데이터를 넘기면서 `PagerContent`가 없었습니다. 그래서 **20만 행을 한 번에 렌더링**하려 했고, 사용자가 1명뿐이어도 **120초 안에 화면이 뜨지 않았습니다.**

데모 데이터(439행)에서는 5초 안에 열려서 문제가 보이지 않았습니다. 데이터 규모를 키워서 측정하지 않았다면 놓쳤을 문제입니다.

### 3-3. 행을 그릴 때마다 전체 목록을 다시 훑음 (O(N²))

```csharp
// 개선 전: '잔여' 칸 색칠 함수. 셀 하나를 그릴 때마다 호출됨
var candidates = _filteredResults
    .Where(c => c.WaferInfo.Equals(x.WaferInfo, ...))   // 전체 목록 순회
    .Select(c => c.UseDate) ...
```

화면에 그리는 행 수 × 전체 목록 크기만큼 연산이 일어났습니다.

### 3-4. 인덱스를 쓸 수 없는 검색 조건

```csharp
// 개선 전: 컬럼에 함수를 씌우고 부분 문자열 검색 → 인덱스를 쓸 수 없음 (Non-SARGable)
context.ChipUsage.Where(m => m.UseDate.ToString().Contains(SearchFilter) ...)
```

게다가 검색어 한 글자를 입력할 때마다 DB 조회가 일어났고, DB에는 PK와 FK 외에 **인덱스가 하나도 없었습니다.**

### 3-5. 대시보드: 모든 사용자가 같은 쿼리를 반복 실행

홈 화면을 열 때마다 쿼리 13개가 실행됐습니다. Blazor는 프리렌더링과 인터랙티브 렌더링에서 초기화를 두 번 하기 때문에, 실제로는 **사용자 1명당 26개**였습니다. 결과는 모든 사용자에게 똑같은데도요.

### 3-6. DbContext 수명 관리

압력 탭으로 전환할 때마다 `context = DbFactory.CreateDbContext()`로 새 컨텍스트를 만들고, 이전 컨텍스트는 해제하지 않은 채 버리고 있었습니다.

### 3-7. 저장 버그: await 없는 SaveChangesAsync (5곳)

```csharp
// 개선 전
private Task<DataGridEditFormAction> CommittedItemChanges(ChipPressure item)
{
    using var context = DbFactory.CreateDbContext();
    context.Attach(item!).State = EntityState.Modified;
    context.SaveChangesAsync();          // 기다리지 않음
    return Task.FromResult(DataGridEditFormAction.Close);
}                                        // 여기서 context 해제
```

저장이 끝나기 전에 `using`이 컨텍스트를 해제할 수 있습니다. 평소에는 DB가 빨라서 운 좋게 저장되지만, **부하가 걸리면 수정 내용이 조용히 사라질 수 있는** 버그입니다. 예외가 나도 아무도 받지 않아서 로그에도 남지 않습니다.

## 5. 측정 중 발견한 추가 문제: 셀 편집 모드의 메모리 비용

개선 후, 압력 탭을 연 사용자는 1인당 메모리가 **157MB**로 여전히 컸습니다. 압력 탭을 열지 않은 사용자는 12MB였습니다. 원인을 찾기 위해 서버 힙 덤프를 분석했습니다.

```
dotnet-gcdump report 결과 (압력 탭 100행 표시, 사용자 1명)
  ComponentState                      8,663개   ← 살아 있는 Blazor 컴포넌트 수
  MudBlazor.State.ParameterMetadata  17,641개
  RenderTreeFrame[]                  약 12MB
```

압력 그리드는 **셀 편집 모드**라서 모든 셀이 입력 컴포넌트(DatePicker, NumericField, Select)로 렌더링됩니다. MudBlazor 입력 컴포넌트는 내부적으로 여러 컴포넌트로 이루어져 있어서, **100행만 보여 줘도 컴포넌트가 약 8,600개** 생겼습니다.

즉 Blazor Server에서는 **"몇 행을 조회하느냐"뿐 아니라 "그 행을 어떤 컴포넌트로 그리느냐"도 서버 메모리를 결정합니다.**

UX는 그대로 두고, 기본 표시 행을 100행에서 25행으로 줄였습니다(50·100행은 선택 가능).

| 압력 탭을 연 사용자 1명 | 100행 | 25행 |
|---|---|---|
| 서버 메모리 | 157 MB | **53 MB** |
| 탭 로딩 | 1.03초 | **0.48초** |

## 7. 측정의 한계

결과를 과장하지 않기 위해 한계를 함께 적습니다.

- **부하 생성기와 서버가 같은 PC에서 돌았습니다.** 개선 후 50명 테스트에서 서버는 평균 약 1.4코어(12초 동안 CPU 16.5초)만 사용했습니다. 따라서 50명일 때의 4~6초 응답은 대부분 **브라우저 50개를 동시에 돌린 클라이언트 쪽 부하**입니다. 반면 개선 전 20명 테스트에서는 서버가 평균 약 6.7코어를 써서 **서버가 실제 병목**이었습니다.
- **LocalDB에서 측정했습니다.** 운영 SQL Server와 절대 시간은 다를 수 있으므로, 개선 전후의 **비율**로 해석하는 것이 정확합니다.
- 개선 후 20명 측정에서 대시보드는 **예열 사용자가 채운 캐시가 유효한 상태**였습니다. 대시보드 쪽 DB 수치에는 캐싱 효과가 포함되어 있습니다.
- 메모리는 강제 GC 직후의 GC 힙 크기입니다. 대용량 힙에서는 `dotnet-gcdump` 수집이 실패해서(.NET 9 이벤트 버퍼 제한), 모든 측정을 같은 방식(강제 GC + `dotnet-counters`)으로 통일했습니다.

## 8. 배운 점

1. **Blazor Server의 비용은 "사용자당 상태 × 동시 접속자"다.** 서버 측 페이징처럼 사용자당 상태를 데이터 양과 무관하게 만드는 것이 가장 효과가 컸습니다.
2. **조회하는 행 수만큼 렌더링하는 컴포넌트 수도 중요하다.** 셀 편집 모드 100행이 컴포넌트 8,600개였습니다. 힙 덤프를 보기 전에는 예상하지 못한 비용이었습니다.
3. **데이터 규모를 키워서 테스트해야 보이는 문제가 있다.** 압력 탭 문제는 데모 데이터에서는 전혀 드러나지 않았습니다.
4. **부하가 걸려야만 드러나는 정확성 버그가 있다.** await 없는 저장은 평소에는 동작하다가, 서버가 바쁠 때만 데이터를 잃습니다.
5. **캐시는 트레이드오프다.** 대시보드는 요약 화면이라 30초 지연을 허용했고, 정확해야 하는 목록 화면은 캐시하지 않았습니다. 데이터가 바뀌면 캐시를 바로 무효화해서 지연을 줄였습니다.

## 9. 앞으로 개선할 점

- 압력 그리드 편집 방식을 셀 편집에서 행 단위 폼 편집(`DataGridEditMode.Form`)으로 바꾸기. 기본 화면은 텍스트로만 그려서 컴포넌트 수를 크게 줄일 수 있지만 UX가 바뀌므로 사용자 의견이 필요합니다.
- 다른 목록 페이지(시약, 장비, 부품, 동결세포)에도 같은 서버 페이징 패턴 적용
- 운영 환경과 같은 사양의 별도 서버에서 부하 테스트를 해서 실제 한계 동시 접속자 수 측정
- 서버를 여러 대로 늘릴 경우 Sticky Session 또는 Azure SignalR Service 검토
